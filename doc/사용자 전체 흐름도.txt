[MVP 사용자 전체 흐름도 v2]

작성일: 2026-05-14
수정 기준:
- Backend DB/API 계약 v1과 충돌하지 않도록 정리한다.
- 1차 결과는 "확정 매칭"이 아니라 "입력값 기준 후보 확인"으로 정의한다.
- 최종 매칭은 파트너 전자증명/증빙 검증 이후에만 가능하다.
- 예상 금액은 계산값이 아니라 공고에 등록된 지원금액 범위의 참고 표시로만 사용한다.
- MVP에서는 AI 자동판단, 자동 추천, 자동 우선순위, 선정확률, 가점 계산을 사용하지 않는다.

1. MVP 전체 원칙
━━━━━━━━━━━━━━━━━━

핵심 구조:
빠른 1차 후보 확인
→ 회원가입 및 동의
→ 구독/결제 Gate
→ 파트너 검증
→ 최종 매칭
→ 단계별 실행관리
→ 결과 기록

운영 원칙:
- 일반 유입과 TM 유입을 분리한다.
- 회원 입력값은 1차 후보 확인용 참고값이다.
- 실제 매칭 기준은 파트너 검증값을 우선 사용한다.
- 전자증명/증빙 확인 전에는 최종 매칭으로 표시하지 않는다.
- 사용자는 각 단계에서 지금 해야 할 행동 1개를 중심으로 진행한다.
- 단계 완료 조건 충족 전 다음 단계 이동은 서버에서 차단한다.

[2] 기본 정보 입력

- 이 API는 개인정보 원문을 장기 저장하지 않는 정책이 필요하다.

[4] 1차 후보 결과 확인

주의:
- 이 단계는 최종 매칭 결과가 아니다.
- 회원 입력값 기준 참고 결과다.
- 파트너 검증 이후 실제 가능 여부가 달라질 수 있다.
- 상세 사업명, 기관명, 접수 위치, 상세 조건은 비공개다.

노출 정보:
- 정책자금 후보 개수
- 지원금 후보 개수
- 보조금 후보 개수
- 공고 기준 지원금액 범위

가족 기준 노출:
- 사업자 기준 후보
- 배우자 기준 후보
- 자녀 기준 후보
- 부모 기준 후보

표현 원칙:
- "예상 수령액", "확정 가능 금액", "추천 사업" 표현을 사용하지 않는다.
- "공고 기준 지원금액 범위", "후보 개수", "검증 전 참고 결과"로 표현한다.

안내 문구:
현재 입력하신 사업 및 가족 정보 기준으로 진행 가능성이 있는 후보가 확인되었습니다.
다만 이 결과는 입력값 기준 참고 결과이며, 전자증명/증빙 확인과 파트너 검증 후 실제 가능 여부가 달라질 수 있습니다.

비공개 정보:
- 실제 사업명
- 기관명
- 접수 위치
- 상세 조건

행동 버튼:

[6] 구독/결제 Gate

상태:
- 제품 방향상 필요하다.
- 현재 Backend DB/API 계약에는 결제/구독 도메인이 아직 없다.

PM 결정:
- MVP에 실제 결제를 포함하려면 Backend 계약에 subscription/payment 테이블과 API를 추가해야 한다.
- 실제 결제를 당장 포함하지 않으면 "상담 예약 전 운영 확인 Gate"로 임시 운영한다.

필요 계약:
- 구독 상태 enum
- 결제 상태 enum
- 과금 시점
- 환불/해지 정책
- 결제 실패 시 진행 제한 정책

Frontend Gate:
- 결제/구독 API 확정 전 결제 화면 구현 금지

━━━━━━━━━━━━━━━━━━

[7] 파트너 첫 상담 예약

예약 진행:
- 상담 시간 선택
- 상담 예약 완료

현재 상태:
- 상담 예약 API는 Backend 계약에 아직 없다.
- MVP에서 필수라면 별도 예약 도메인 계약이 필요하다.
- 계약 전에는 파트너 검증 생성 시점에 운영자가 수동 배정하는 방식으로 제한한다.

━━━━━━━━━━━━━━━━━━

- 매출/직원/상시근로자
- 세금 상태
- 신용/금융 조회 결과

Backend 의존성:
- `/api/v1/partner-verifications`
- `/api/v1/partner-verifications/{verificationId}/member-values`
- `/api/v1/partner-verifications/{verificationId}/business-values`

[10] NICE / KCB 조회 결과 입력

조회 정보:
- NICE 신용점수
- KCB 신용점수
- 기대출 내역
- 정책자금 이용 여부
- 보증기관 이용 여부

[11] 간단 인터뷰

최종 확인 질문:
- 기존 동일 사업 진행 여부
- 정책자금 이용 여부

제한 플래그:
- 예외/제한 항목 체크 시 정책자금 매칭 제외 또는 검토 필요로 분류한다.

Backend 의존성:
- `/api/v1/partner-verifications/{verificationId}/restriction-flags`

━━━━━━━━━━━━━━━━━━

[12] 최종 매칭 확인

조건:
- 파트너 검증 상태가 `VERIFIED`여야 한다.
- 공고 승인 상태가 `APPROVED`여야 한다.
- 제한 플래그가 차단 조건이면 매칭은 `BLOCKED` 또는 `REVIEW_REQUIRED`로 분류한다.

노출:
- 최종 진행 가능 항목
- 검토 필요 항목
- 제외 항목
- 조건별 통과/실패/스킵 사유

금지:
- 추천도 표시 금지
- 우선순위 표시 금지
- 선정확률 표시 금지
- 가점 표시 금지

Backend 의존성:
- `/api/v1/matching/cases`
- `/api/v1/matching/cases/{matchingCaseId}`
- `/api/v1/matching/cases/{matchingCaseId}/results`

━━━━━━━━━━━━━━━━━━

[13] 진행 시작

진행 구조:
- 매칭 케이스에서 진행을 시작한다.
- 현재 해야 할 행동 1개 중심으로 표시한다.
- 체크리스트 완료 전 완료 버튼은 비활성 상태다.
- 완료 조건 충족 후에만 다음 단계로 이동한다.

Backend 의존성:
- `/api/v1/application-progresses`

━━━━━━━━━━━━━━━━━━

[14] 단계별 진행 구조

기본 단계:
1단계: 안내/진행 의사 확인
2단계: 서류 준비
3단계: 접수 전 최종 확인
4단계: 접수 진행
5단계: 접수 완료/결과 대기
6단계: 결과 입력

공고별 설정:
- 단계명
- 안내 문구
- 필요 서류
- 행동 버튼
- 완료 조건
- 다음 단계 이동 조건

Backend 의존성:
- `/api/v1/application-progresses/{progressId}`
- `/api/v1/application-progresses/{progressId}/steps/{stepId}/action`
- `/api/v1/application-progresses/{progressId}/steps/{stepId}/documents`
- `/api/v1/application-progresses/{progressId}/receipt`
- `/api/v1/application-progresses/{progressId}/result`

━━━━━━━━━━━━━━━━━━

[15] 리마인드 구조

발송 조건:
- 현재 단계 미진행
- 필수 체크리스트 미완료
- 접수 마감 임박

기본 발송:
- 24시간 리마인드
- 48시간 리마인드
- 공고 마감 2일 전 리마인드

예외:
- 상시 접수 공고는 마감 리마인드 제외
- 리마인드 발송은 `progress_reminder_logs`에 기록한다.

━━━━━━━━━━━━━━━━━━

[16] 신규 가능 항목 알림

발송 조건:
- 신규 공고 등록
- 기존 공고 조건 변경
- 사용자/가족/검증값 변경
- 정기 재검증 완료

MVP 제한:
- 자동 추천이 아니라 신규 후보 발생 알림으로 표현한다.
- 우선순위나 선정확률은 계산하지 않는다.

━━━━━━━━━━━━━━━━━━

[17] 장기 미진행 처리

처리:
- 장기 미진행 시 `STOPPED` 또는 내부 재접촉 대상 상태로 분류한다.
- TM 재접촉 대상 분류는 내부 운영 목록으로만 사용한다.

필요 계약:
- 장기 미진행 기준일
- 재접촉 대상 상태값
- 사용자에게 노출할 상태 문구

[18] 정기 상태값 갱신

권장 주기:
- 6개월

안내 문구:
최근 검증일 기준 일정 기간이 경과했습니다.
사업 상태, 세금 상태, 금융 상태 등 실제 조건이 변경되었을 수 있으므로 정확한 매칭을 위해 정보 재확인이 필요합니다.
최근 전자증명 및 상태값을 다시 갱신해 주세요.

주의:
- 최신 검증값이 아니면 일부 후보 결과가 실제 조건과 다를 수 있다.
- 만료된 검증값은 최종 매칭 기준으로 사용하지 않는다.

━━━━━━━━━━━━━━━━━━
4. TM 유입 흐름
━━━━━━━━━━━━━━━━━━

TM 연결
→ 회원/사업자 기본 정보 확인
→ 파트너 검증 입력
→ 전자증명/필수서류 확인
→ NICE / KCB 조회 결과 입력
→ 간단 인터뷰
→ 최종 매칭 확인
→ 구독/결제 Gate
→ 진행 시작
→ 단계별 진행
→ 결과 확인

TM 유입 원칙:
- TM 유입은 1차 후보 확인과 회원가입 전환 단계를 단축할 수 있다.
- 그러나 파트너 검증과 최종 매칭 Gate는 생략할 수 없다.
- 결제/구독 Gate는 Backend 계약 확정 전까지 구현하지 않는다.

━━━━━━━━━━━━━━━━━━
5. Backend 계약 보완 필요 항목
━━━━━━━━━━━━━━━━━━

현재 `docs/backend/api-contract-v1.md`에 없는 항목:
- 회원가입 전 임시 후보 확인 API
- 사용자 대시보드 요약 API
- 구독/결제 상태 API
- 상담 예약 API
- 장기 미진행/TM 재접촉 목록 API

PM 판단:
- MVP 1차 구현에서 결제와 상담 예약을 실제 기능으로 넣을지 먼저 확정해야 한다.
- 결제와 예약을 포함한다면 Backend DB/API 계약을 먼저 확장한다.
- 포함하지 않는다면 운영 수기 Gate로 두고 Frontend에는 상태 안내만 노출한다.
