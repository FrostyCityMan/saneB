[MVP 사용자 대시보드 구조 정리 v2]

작성일: 2026-05-14
목적:
- 사용자가 지금 해야 할 행동을 즉시 이해하도록 한다.
- 1차 후보, 파트너 검증, 최종 매칭, 진행관리 상태를 혼동하지 않도록 분리한다.
- Backend API 계약이 확정되지 않은 값은 화면 구현 전 Gate로 표시한다.

━━━━━━━━━━━━━━━━━━
1. 대시보드 핵심 원칙
━━━━━━━━━━━━━━━━━━

- 첫 화면은 "숫자"보다 "현재 해야 할 행동"을 우선한다.
- 예상 수령액처럼 확정적으로 읽히는 표현을 사용하지 않는다.
- 금액은 공고 기준 지원금액 범위의 참고 표시로만 노출한다.
- 최종 매칭 전에는 "후보"와 "검증 필요" 상태를 명확히 표시한다.
- 진행 단계는 사용자가 지금 완료해야 할 행동 1개를 중심으로 보여준다.
- 모바일 360px 기준에서는 상단 요약 → 현재 행동 → 진행 현황 순서로 배치한다.

━━━━━━━━━━━━━━━━━━
2. 대시보드 정보 구조
━━━━━━━━━━━━━━━━━━

[상단] 상태 요약

노출 항목:
- 현재 서비스 상태
- 1차 후보 개수
- 최종 매칭 개수
- 공고 기준 지원금액 범위
- 검증 상태

상태 예시:
- 후보 확인 전
- 회원가입 필요
- 구독/결제 확인 필요
- 파트너 검증 필요
- 검증 진행중
- 최종 매칭 확인 필요
- 진행중
- 결과 대기
- 재검증 필요

문구 원칙:
- "정책자금 3건" 대신 "정책자금 후보 3건"으로 표시한다.
- "예상 가능 금액" 대신 "공고 기준 지원금액 범위"로 표시한다.
- "확정" 표현은 파트너 검증과 최종 매칭 완료 후에만 사용한다.

예시:
- 정책자금 후보 3건
- 지원금 후보 2건
- 공고 기준 지원금액 범위 3,000만원 ~ 7,000만원
- 전자증명 검증 전 참고 결과

━━━━━━━━━━━━━━━━━━

[중단] 현재 해야 할 행동

목적:
- 사용자가 다음 클릭을 고민하지 않도록 단일 행동을 제시한다.

우선순위:
1. 비밀번호 변경 필요
2. 회원가입/동의 미완료
3. 구독/결제 Gate 미완료
4. 파트너 상담/검증 필요
5. 전자증명/서류 확인 필요
6. 신용조회 동의 또는 조회 결과 입력 필요
7. 최종 매칭 확인 필요
8. 진행 단계의 현재 행동
9. 접수번호/접수일 입력 필요
10. 결과 입력 필요
11. 정기 재검증 필요

카드 구성:
- 행동 제목
- 행동 설명
- 마감 또는 권장 완료일
- 주요 버튼 1개
- 보조 버튼 1개 이하

예시:
- 사업자등록증 확인이 필요합니다.
- NICE/KCB 조회 결과 확인이 필요합니다.
- 현재 공고의 접수 진행을 완료해 주세요.
- 결과 입력이 필요합니다.

버튼 예시:
- 서류 확인하기
- 검증 진행하기
- 최종 매칭 확인하기
- 접수 진행하기
- 결과 입력하기

━━━━━━━━━━━━━━━━━━

[하단] 진행 현황

노출 항목:
- 진행중 건수
- 결과 대기 건수
- 승인 건수
- 보완 요청 건수
- 중단 건수
- 누적 수령 금액

주의:
- 누적 수령 금액은 사용자가 직접 입력하거나 파트너/운영자가 결과로 확인한 금액만 합산한다.
- 공고 기준 지원금액 범위와 누적 수령 금액을 섞지 않는다.

예시:
- 진행중 2건
- 결과 대기 1건
- 승인 1건
- 누적 수령 금액 500만원

━━━━━━━━━━━━━━━━━━
3. 상태별 대시보드 구조
━━━━━━━━━━━━━━━━━━

[A. 회원가입 전]

상단:
- 1차 후보 개수
- 공고 기준 지원금액 범위
- 검증 전 참고 결과 표시

중단:
- 회원가입 후 계속 진행하기

하단:
- 상세 사업명/기관명/접수 위치 비공개

Backend 필요:
- 회원가입 전 임시 후보 확인 API

━━━━━━━━━━━━━━━━━━

[B. 회원가입 후 / 검증 전]

상단:
- 후보 개수
- 검증 상태: 미검증

중단:
- 전자증명 동의 또는 파트너 검증 시작

하단:
- 준비해야 할 서류 요약

Backend 필요:
- `/api/v1/auth/me`
- `/api/v1/members/me/profile`
- `/api/v1/members/me/business-profile`
- `/api/v1/members/me/family-members`

━━━━━━━━━━━━━━━━━━

[C. 파트너 검증 진행중]

상단:
- 검증 상태
- 누락 서류 수
- 제한 플래그 여부

중단:
- 현재 필요한 검증 행동 1개

하단:
- 서류 체크리스트
- 신용/금융 조회 상태

Backend 필요:
- `/api/v1/partner-verifications/{verificationId}`
- `/api/v1/partner-verifications/{verificationId}/documents`
- `/api/v1/partner-verifications/{verificationId}/restriction-flags`

━━━━━━━━━━━━━━━━━━

[D. 최종 매칭 완료]

상단:
- 최종 진행 가능 항목 수
- 검토 필요 항목 수
- 제외 항목 수

중단:
- 진행 시작하기

하단:
- 항목별 통과/실패/스킵 요약

Backend 필요:
- `/api/v1/matching/cases/{matchingCaseId}`
- `/api/v1/matching/cases/{matchingCaseId}/results`

━━━━━━━━━━━━━━━━━━

[E. 진행중]

상단:
- 현재 진행 공고명
- 현재 단계
- 마감일 또는 권장 완료일

중단:
- 현재 해야 할 행동 1개

하단:
- 단계별 상태
- 체크리스트
- 리마인드 상태

Backend 필요:
- `/api/v1/application-progresses`
- `/api/v1/application-progresses/{progressId}`
- `/api/v1/application-progresses/{progressId}/steps/{stepId}/action`
- `/api/v1/application-progresses/{progressId}/steps/{stepId}/documents`

━━━━━━━━━━━━━━━━━━

[F. 결과 대기 / 결과 입력]

상단:
- 접수 완료 상태
- 예상 결과 일정

중단:
- 결과 입력하기

하단:
- 접수번호
- 접수일
- 결과 메모

Backend 필요:
- `/api/v1/application-progresses/{progressId}/receipt`
- `/api/v1/application-progresses/{progressId}/result`

━━━━━━━━━━━━━━━━━━

[G. 재검증 필요]

상단:
- 최근 검증일
- 재검증 필요 사유

중단:
- 최신 전자증명/상태값 갱신하기

하단:
- 변경 가능성이 있는 항목
- 세금 상태
- 금융 상태
- 가족 정보

Backend 필요:
- 검증 만료 기준
- 검증 재요청 API 또는 기존 partner verification 재생성 정책

━━━━━━━━━━━━━━━━━━
4. Backend API 보완 필요
━━━━━━━━━━━━━━━━━━

현재 Backend API 계약에 추가 검토가 필요한 대시보드 전용 계약:

1. `GET /api/v1/dashboard/me/summary`
   - 사용자 상태 요약
   - 후보 개수
   - 최종 매칭 개수
   - 공고 기준 지원금액 범위
   - 검증 상태

2. `GET /api/v1/dashboard/me/current-action`
   - 현재 해야 할 행동 1개
   - 버튼 코드
   - 이동 route
   - 마감/권장 완료일

3. `GET /api/v1/dashboard/me/progress-summary`
   - 진행중 건수
   - 결과 대기 건수
   - 승인 건수
   - 보완 요청 건수
   - 중단 건수
   - 누적 수령 금액

4. `GET /api/v1/dashboard/me/reverification-status`
   - 최근 검증일
   - 검증 만료 여부
   - 재검증 필요 항목

━━━━━━━━━━━━━━━━━━
5. Frontend 구현 Gate
━━━━━━━━━━━━━━━━━━

구현 착수 전 확정 필요:
- 사용자 대시보드 defaultRoute
- 대시보드 summary API
- 현재 행동 우선순위
- 후보 결과와 최종 매칭 결과의 표현 차이
- 구독/결제 상태값 포함 여부
- 상담 예약 기능 포함 여부
- 누적 수령 금액 산정 기준

구현 금지:
- Backend 계약 없이 숫자 임의 계산
- Frontend에서 매칭/우선순위/선정확률 계산
- `th:utext` 사용
- secret, token, 외부 API key 브라우저 노출
