## 비교할 가설과 실제 결과

현재 `SeodaemunAttachmentDiscoveryProfile`은 공식 링크의 인자를 UTF-8로 정규화하고 키를 정렬한다. 과거 공식 상세는 EUC-KR였다. 인코딩 또는 인자 표기 차이가 시간 초과의 원인인지 확인하기 위해 **기존 고정 공고·공식 다운로드 링크의 첫 파일만** 비교했다. 새 공고 번호·파일 경로를 추측하지 않았다.

| 비교 / 관측 시작(UTC) | 상세 | 파일 요청 | 결과 |
|---|---|---|---|
| 정렬된 인자 / 06:05:15.796775 | HTTP200·92,519byte, EUC-KR, 다운로드4링크 | UTF-8 1회, EUC-KR 1회 | 모두 curl28·HTTP000·수신0byte |
| 공식 인자 순서와 경로 표기 보존 / 06:06:25.166414 | HTTP200·92,519byte, EUC-KR, 다운로드4링크 | UTF-8 1회, EUC-KR 1회 | 모두 curl28·HTTP000·수신0byte |

공식 href에는 퍼센트 이스케이프가 없고 비ASCII 문자가 있었다. 키 순서는 `path`, `oriFileNm`, `saveFileNm`이며 `path=/board/82`는 슬래시를 그대로 포함했다. 두 번째 비교는 공식 href의 ASCII 구분자·순서를 보존하고 비ASCII 문자를 인코딩했다. 응답 실패는 특정 인코딩을 올바르다고 입증하지 않으며 서버 장애나 접근 차단 원인도 확정하지 못한다. HTTP000은 서버의 HTTP 오류 코드가 아니라 응답 상태를 받지 못한 curl 결과다.

상세 SHA256은 첫 비교 `734bd953fe0b6202bbe277ba0e8ed15e977171dda3bd2bd2e41642ce08294287`, 두 번째 비교 `1758697619855596e568577a2ccad3c2f35884a511f1a50506acddaf229bbd7a`다. 동적 페이지 hash 차이를 첨부 파일 변경으로 해석하지 않는다. 파일 바이트가 없으므로 signature·실파일 hash·추출 근거는 없다.

## 실행 한도와 보존 범위

`build/qa-tools/survey-seodaemun-query-encoding.py`와 `--official-query-shape`를 각각1회 실행했다. 각 실행은 상세1GET(2MiB)·파일2GET(각16MiB), 총3요청·34MiB 상한이다. 합계6요청·68MiB, 실제 수신185,038byte(상세만)다. 요청당15초·연결8초·프로세스20초, 자동 재시도0·redirect0, Windows 신뢰 저장소의 TLS 검증을 유지했다. User-Agent는 기존 `saneB-notice-collector/1.0`이며 브라우저 위장·쿠키·인증 우회는 없다.

원본 HTML·파일은 디스크에 저장하지 않았다. 원시 URL 인자·파일명·응답 헤더·오류 원문을 로그에 남기지 않았다. 두 Python/curl 실행은 종료0으로 끝났지만 이는 진단 보고서를 반환했다는 뜻이며 파일 다운로드 성공이 아니다. 성공 영수증 인덱스나 지역 성공 수를 변경하지 않았다. 이전 모든 실패와 이번6요청은 별도 이력으로 유지한다.
