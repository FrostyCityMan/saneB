# 지자체 공고 수집 잔여 출처 복구 설계

## 1. 현재 상태

- 정적 지자체 출처는 244곳이다.
- 2026-07-14 전수 QA 기준 `VERIFIED` 242곳, `CHECK_REQUIRED` 2곳, `FAILED` 0곳이었다.
- 2026-07-16 재검증에서 중랑구청 `LGS-000008`, 금천구청 `LGS-000019`의 실제 대체 URL을 확인했다.
- 같은 전수 QA에서 성남·안양·속초는 Java TLS 호환 문제가 재현됐고 창원은 공식 메뉴 경로가 변경된 것을 확인했다.
- 모든 출처는 운영자 승인 전까지 `is_enabled=false`를 유지한다.

## 2. 원인과 복구 방향

### 중랑구청

- 기존 공모사업 알림방은 목록 구조를 읽을 수 있지만 최근 1년 이내 게시물이 없다.
- 현재 운영되는 공식 공고/고시 목록으로 URL을 교체한다.
- 새 목록은 기존 공통 `SPRING_BBS` 프로필로 제목, 등록일, 상세 URL을 모두 추출한다.
- 비표준 응답 헤더 호환을 위해 기존 `LEGACY_BROWSER` 요청 프로필은 유지한다.

### 금천구청

- 기존 소상공인 지원사업 목록은 일부 행에 등록일 대신 신청기간만 제공한다.
- 등록일을 명시하는 공식 고시·공고 목록으로 URL을 교체한다.
- 현재 공통 `SAEOL_GOSI` 프로필로 제목, 등록일, 상세 URL을 모두 추출하므로 별도 파서를 만들지 않는다.

### 성남시청

- 사용자 바로가기는 성남시 공식 HTTPS 고시공고 화면을 사용한다.
- 공식 화면이 삽입하는 새올 공고 목록은 공개 HTTP action endpoint에 기존 form POST로 요청한다.
- 기존 `SAFE_SAEOL_EMINWON` 프로필과 `BROWSER_HTTP1` 요청 프로필을 유지한다.

### 안양시청

- 사용자 바로가기는 안양시 공식 HTTPS 고시공고 화면을 유지한다.
- 수집은 동일 공고를 제공하는 공개 HTTP 새올 endpoint를 사용해 Java TLS handshake 문제를 분리한다.
- 실제 열 구조에 맞는 `SAFE_SAEOL_EMINWON_CELL` 프로필을 사용한다.

### 속초시청

- 사용자 바로가기는 현재 속초시 공식 HTTPS 고시·공고 화면으로 교체한다.
- 수집은 동일 공고를 제공하는 공개 HTTP 새올 endpoint를 사용한다.
- 기존 `SAFE_SAEOL_EMINWON` 프로필을 재사용한다.

### 창원시청

- 폐기된 기존 메뉴를 현재 공식 고시공고 URL로 교체한다.
- 기존 `SPRING_BBS` 프로필로 제목, 등록일, 상세 URL을 모두 추출한다.

## 3. DB 변경

- `V55__recover_remaining_local_government_notice_sources.sql` additive migration을 추가한다.
- `LGS-000008`, `LGS-000019`, `LGS-000089`, `LGS-000094`, `LGS-000122`, `LGS-000224`의 URL, 수집 endpoint, 파서 연결을 보정한다.
- 전수 QA에서 확인된 `LGS-000026`, `LGS-000034`의 지연 endpoint와 `LGS-000036`, `LGS-000167`, `LGS-000174`의 HTTP-to-HTTPS 전환도 같은 additive migration에서 보정한다.
- 대상 출처를 `VERIFIED/READY/OFF`로 전환하고 과거 오류 정보만 초기화한다.
- 수집 이력, 원문 데이터, 운영 공고 데이터는 삭제하거나 변경하지 않는다.

## 4. 변경하지 않는 계약

- `/api/v1` 경로와 응답 구조는 변경하지 않는다.
- 최근 1년 이내 등록일 필터를 완화하지 않는다.
- 신청 시작일이나 접수기간을 등록일로 대체하지 않는다.
- 출처를 자동 활성화하지 않는다.
- 자동 수집 공고를 자동으로 운영 공고에 활성화하지 않는다.

## 5. 검증 Gate

1. 구조 변경 6곳과 전송 보정 5곳의 실사이트 QA에서 기존 공통 프로필만으로 제목, 등록일, 동일 기관 상세 URL을 추출한다.
2. 244곳 전수 QA에서 `PASS 244`를 확인한다.
3. PostgreSQL Flyway 통합 테스트에서 V55 적용과 `VERIFIED 244`, `CHECK_REQUIRED 0`, `OFF 244`를 확인한다.
4. 전체 테스트와 `bootJar`, Backend Gate를 통과한다.
5. 배포 후 Actuator health와 관리자 출처 목록에서 보정 대상 11곳이 `READY/OFF`인지 확인한다.

## 6. 롤백 원칙

- Flyway 운영 migration은 되돌려 쓰지 않는다.
- 실사이트 구조가 다시 변경되면 후속 additive migration으로 URL 또는 프로필을 보정한다.
- 장애가 발생하면 해당 출처만 OFF로 유지하고 나머지 출처의 수집 계약에는 영향을 주지 않는다.
