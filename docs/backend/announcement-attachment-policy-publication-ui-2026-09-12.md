# 첨부 정책 게시 준비·실행 화면

## 상태와 사용자 과업

Gate 4 부분 구현, 전체 Not ready다. 기존 Thymeleaf/Bootstrap 정책 관리 화면에 V76 준비 원장과 V77 게시 영수증을 연결한다. 전체 Provider·worker DB QA 실행기/증거 검증기, 실제 PostgreSQL/Linux, 운영 게시·역할별 브라우저 E2E는 필수 잔여다. 합성 화면의 VERIFIED와 게시 성공은 실제 운영 근거가 아니다.

Design Read: 기존 업무 화면에서 영향 조회 → 정확한 범위 고정 → 개별 영향 확인 → 게시 영수증 확인을 구분한다. 주요 사용자는 정책을 관리하는 ADMIN이며 OPERATOR/APPROVER는 이력 조회만 한다. 한국어·서울 시각, 데스크톱 업무와 모바일 조회를 가정한다. R2 고위험 정책 변경으로 취급하며 P0 데이터 무결성·권한과 P1 오류 회복을 시각 효과보다 우선한다. 새 의존성·모션·상태 라이브러리는 도입하지 않는다.

## 구현 계약

- 기존 `/app/admin/announcement-attachment-policies`와 기존 스크립트 2개를 유지한다. 기존 v1 규칙 API는 목록 조회만 사용한다.
- 준비 목록·상세·항목은 `/publication-scopes`의 실제 API를 사용한다. 목록 10개, 항목 20개씩 페이지별로 전체 범위를 탐색한다. scopeId/scopePage/scopeItemPage를 URL에 보존하고 기본 선택도 ID로 고정한다. 고정 항목은 POLICY/SOURCE/JOB/COLLECTION_PLAN/COLLECTOR의 ID와 상태 hash만 표시한다. 혼합 항목 수를 공고 수로 표시하지 않는다.
- 준비 POST는 조회한 초안 버전과 사유만 전송한다. 임의 ID 목록·hash·QA 성공 입력을 보내지 않는다. 준비 응답은 isApproval=false/0 HTTP이고 실제 게시 버튼을 자동 실행하지 않는다. 준비는 10분 유효하며 생성한 관리자만 실제 게시할 수 있다. 다른 관리자 여부는 서버가 최종 검증한다.
- 실제 게시의 UI 진입 조건은 최신 DRAFT/ACTIVE 규칙, 전체 4단계 VERIFIED, QA/정책/규칙/범위 지문 일치, 유효하고 현재인 준비 범위, 미저장 입력 없음이다. UI 조건 충족은 서버의 전체 증거·설치·범위 검증을 대신하지 않는다. 현재 미연결 전체 QA는 우회할 수 없다.
- 실제 게시 승인에는 일반 작업 확인과 별도로 신규 수집 영향, 기존 고정 작업 보존, 기존 데이터 별도 처리의 세 체크박스를 모두 요구한다. 기본 체크는 없다. 게시 모드·범위 ID/hash·항목 수·만료·QA·이전 정책·공고별 byte 상한·OFF 전역 영향·복구 절차를 미리 표시한다.
- 게시 API 자체의 외부 요청 0회와 별도 상시 worker의 향후 외부 요청을 구분한다. 이 요청은 worker 설정·기존 데이터 일괄 적용·공고 자동 활성화 endpoint를 호출하지 않는다. 게시 정책을 다시 바꾸려면 새 개정·QA·게시 절차를 사용한다.
- 게시 응답은 정책 ID, 게시 버전=요청 버전+1, scope ID/hash, QA ID/hash, mode와 비일괄처리 flags를 대조한다. 모순된 응답은 성공으로 표시하지 않는다. 영수증의 이전 버전은 퇴역 전 버전이다.
- 별도 GET 영수증은 당시 성공 이력이며 현재 ACTIVE 상태를 증명하지 않는다. 404는 영수증 없음, 그 외 실패는 미확인으로 표시한다. V77 이전 게시 정책은 영수증이 없을 수 있다.

## 실패·회복·접근성

- 준비와 실제 게시는 서로 다른 UUID 멱등 키를 사용한다. 네트워크/5xx/응답 모순은 미확정으로 잠그고 원래 body/key로만 재확인한다. 후속 401/403/409도 미확정 요청을 새 요청으로 바꾸지 않는다. 만료 후 재확인도 같은 key로 이미 저장된 영수증을 조회할 수 있다.
- 초기 확정 409는 입력을 보존하고 최신 조회를 요구한다. 준비·QA·상세 일부 조회 실패는 게시를 차단하며 빈 데이터/성공으로 숨기지 않는다. 성공 응답 뒤 최신 조회가 실패해도 확인된 영수증 ID와 당시 버전은 요청 결과 영역에 남긴다.
- 폼 편집/새 검토는 기존 동의를 해제한다. 만료는 submit 시 재검사한다. 수동 새로고침/후속 조회가 필요하며 짧은 브라우저 주기로 외부 요청을 반복하지 않는다.
- 네이티브 fieldset/legend/checkbox, 지속 한글 라벨, required, disabled 사유, role=status/alert, 확인 취소 후 호출 버튼으로 포커스 복귀를 사용한다. 요청 후 영수증 영역으로 포커스를 이동한다.
- 원문·사유·요청 키를 localStorage/sessionStorage 또는 URL에 저장하지 않는다. 페이지 종료 시 미저장 입력/미확정 요청 경고를 표시한다. 영수증은 정책 상세의 GET으로 다시 조회한다. 원래 준비 요청 키는 탭 종료 후 복구할 수 없으므로 오류 중에는 탭을 유지하도록 안내한다.
- 표시에는 textContent를 사용하고 임의 evidence JSON, URL, 파일명, 비밀정보를 출력하지 않는다. 서버 권한/CSRF/최종 QA/CAS가 실제 보안 경계다.

## 검증 계획과 판정 범위

- Node 계약/이벤트 테스트: 범위 형식·만료, 누락 QA·버전/hash 불일치, 정확한 POST 필드, 세 개별 동의, 영수증 결합, 응답 유실/동일 키, 읽기 역할, 부분 조회 실패, 과거 영수증.
- 실제 Spring Security/Thymeleaf smoke test: 3개 내부 역할 SSR, 외부 역할/비로그인 거부, 기본 disabled/미체크 확인, no-store/정적 스크립트/한글 설명. API·DB 실제 게시 성공을 증명하는 테스트는 아니다.
- 로컬 합성 브라우저: 명시적으로 내보낸 실제 템플릿과 고정 대역 API를 loopback에서만 제공한다. normal/readonly/publish-ready/lost-publication/expired-scope 등의 시나리오로 업무 흐름·반응형·키보드·오류를 확인한다. 운영 인증·DB·게시·실파일과는 연결하지 않는다.
- 실제 실행 건수·명령·브라우저 확인 결과·남은 접근성 한계는 전체 진행 문서의 최신 실행 기록에 기록한다. 자동 테스트만으로 스크린리더/운영 E2E/전체 Gate 완료를 선언하지 않는다.

SHOULD 예외: 요청 사유/키의 브라우저 영속 저장은 비밀정보·잘못된 계정 재사용 방지를 위해 하지 않는다. 탭 이탈 경고, 원래 요청 재시도, 서버 영수증 조회가 대체 장치다. 실제 운영 사용성/보조기술 검증은 별도 잔여다.
